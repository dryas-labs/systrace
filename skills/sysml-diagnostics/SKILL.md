---
name: sysml-diagnostics
description: Read a SysML/KerML project's context, observe current-window diagnostics in VS Code Chat, or recompute diagnostics for saved files and proposed text from an external Agent, with a bundled language engine, discovery overrides and reusable configuration.
---

- **Inside VS Code Chat:** When `dryas_editor_diagnostics` (`#systraceProblems`) is available, use it for current red lines or Problems. The extension calls `vscode.languages.getDiagnostics()` and returns `observation: "editor"`, including unsaved documents and connection states. It includes all SysML/KerML diagnostic providers, retaining source, related information and diagnostic tags. Disconnection can leave old diagnostics in the panel. The tool belongs to that window.
- **External Agents, including standalone Codex:** Use [the launcher](scripts/run-diagnostics.cjs) for an independent LSP session. It uses the bundled runtime by default and delegates to [the supplied diagnostic script](scripts/diagnostics.cjs). This Skill does not expose the window tool or editor buffers. VS Code Chat can also use it for saved-file checks. If Node cannot access the installed scripts and copying is permitted, copy the complete portable Skill, including its runtime, into a permitted directory; copying only the scripts requires an explicit accessible engine path. Local configuration is not included in distributable packages.
- **Project:** Use a known root directly with `--project <folder>`, or `--project .` when the working directory is the intended root. Existing configuration still applies; without configuration the model scope defaults to `["."]`. Do not infer the root from imports. Use `--context` only when the scope needs inspection: it searches the working directory and its ancestors for `.systrace/project.json` or `.vscode/settings.json` containing `dryas.modelRoots`, without starting an engine. On `PROJECT_NOT_FOUND`, obtain the intended root and pass `--project`; do not expand into sibling projects or disk scans. Discovery does not identify VS Code's active project.
- **Bundled engine:** Run `node <skill-directory>/scripts/run-diagnostics.cjs --project <folder>`. The complete portable Skill contains `runtime/<platform>-<arch>/sysml-lsp[.exe]` and `sysml-grpc[.exe]`; inside the VSIX, the launcher uses the extension's `runtime` directory. These are fixed relative locations, not installation scans. Fresh installs need no executable configuration. `--engine-context` reports the selected source without starting LSP; a bundled executable is displayed relative to the Skill. The binaries must match the agent's operating system and architecture.
- **Discovery overrides:** The launcher preserves 0.1.25 overrides: `--lsp`, `SYSML_LSP_PATH`, and explicit or remembered local configuration take precedence over the bundle. If no bundle or explicit source is available, it checks standard user settings locations for VS Code, VS Code Insiders, Cursor and VSCodium (`dryas.lspPath`), then PATH. It reads JSONC without executing settings and never uses project/workspace executable settings automatically. Distinct editor engine paths require an explicit selection. Do not scan drives or enumerate extension installations. Reading settings locates an executable, not an editor session.
- **Configure once:** Use `node <skill-directory>/scripts/run-diagnostics.cjs --configure-lsp <executable>` to validate accessibility and remember the target machine's path in ignored `engine.local.json`. This file is excluded from VSIX and Skill ZIP output. To follow a selected editor/profile's future settings changes, use `--configure-vscode-settings <settings.json>` instead. These commands replace only this skill's local engine configuration; they do not edit VS Code settings or PATH. For one run, use `--vscode-settings <settings.json>`; it overrides the remembered skill configuration, but `--lsp` and `SYSML_LSP_PATH` still take precedence. `SYSML_VSCODE_SETTINGS` selects a settings file when no remembered `lspPath` applies. Profiles, portable editors, custom user-data directories and remote settings require a known settings file. Paths support `~`, `${env:NAME}` and `%NAME%`. Keep machine-specific paths out of committed project files. If the skill directory is read-only, use an environment variable or explicit flag instead.
- **Engine availability:** `--engine-context` prints the selected executable, its source, checked settings files and discovery issues without launching LSP. On `ENGINE_NOT_FOUND` or an inaccessible configured path, report the exact failure and obtain/configure an executable accessible to this agent. A container or remote agent cannot use a host path unless it is mounted and the binary can run there. Access errors require the environment's supported access mechanism. Do not silently replace the requested diagnostic check with manual inspection; manual findings may supplement it, but report that LSP checking remains blocked. Discovery verifies file access; the diagnostic script still checks engine version and startup.
- **Run and retain:** Capture the complete stdout JSON once; parse and reuse it for counting, grouping and reporting. Engine-selection messages go to stderr without printing the default runtime's absolute installation path. Rerun for changed inputs or a needed fresh observation, not merely to retrieve or reformat the same result. Check `project.root`, `project.modelRoots` and `references`. The result uses `observation: "lsp-recompute"`. `--overlay <project-relative-existing-file>` reads proposed UTF-8 text from stdin without writing files. `--path` filters output, not loaded scope. All original diagnostic options are forwarded; direct `diagnostics.cjs` or `dryas-lsp-diagnostics` still require `--lsp` or PATH and do not use this launcher's discovery.
- **Interpretation:** Distinguish syntax diagnostics from name-resolution and other semantic diagnostics. Engine suggestions are unverified candidates. Empty diagnostics and `settled: true` do not prove complete checking; `settled: false` means the quiet-period condition was not met. Exit 0 can include errors. Both observations use 1-based UTF-16 positions, separate from saved-project API `validate` and its UTF-8 byte columns.
